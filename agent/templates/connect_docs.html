Admiry — connector documentation

Admiry is an AI marketing agent for local and service businesses. This page is written for the assistant (Meta Muse, ChatGPT, Claude) that will build a bridge to it. Everything here is also at /connect/llms.txt (plain text) and /connect/tools.json (tool schemas).

Endpoint

MCP server{{ mcp_url }} — Model Context Protocol, streamable HTTP, stateless (every POST stands alone; JSON responses)
AuthOAuth 2.1, no key. Connect with no credential: the first request answers 401 with WWW-Authenticate: Bearer resource_metadata={{ base }}/.well-known/oauth-protected-resource/mcp; register a client at the authorization server's registration endpoint (dynamic client registration, no secret), use PKCE S256, open the authorization URL for the owner (they sign in with Google and allow), exchange the code at the token endpoint; a refresh token comes with it. Do not ask the owner for a key. Only a client that cannot open a browser for the owner falls back to Authorization: Bearer ak_… (or X-API-Key: ak_…), a key the owner copies from {{ base }}/connect.
Rate limits60 calls per minute and 2,000 per day per key; over the limit the error text carries retry_after=<seconds>.
Version{{ version }} — get_marketing_state returns it as surface_version. If you saved an older one, read this page and the guide again.

How a conversation goes

The guide: {{ skill_url }} (the files it names are beside it, under {{ base }}/connect/references/). In short: get_marketing_state first, and follow its next. For a business with nothing begun that is create_marketing_plan → update_marketing_plan (until the plan can be shown) → get_marketing_plan → launch_marketing_plan; called for a business that already has a plan, create_marketing_plan starts over. Every result is {data, say, next}: show say as written, present next, send the owner's own words back.

For a home-services business or a dental practice, the page the ads use can be a whole website Admiry builds: get_site_templates shows its three looks, update_landing_page with action "build_site" (or "write") asks its questions one at a time (the look first, then the facts it lacks) and builds it, and get_landing_page with view "site" shows where it stands. A photo reaches Admiry only through the upload link the answer carries.

Tools

RO reads · W writes · P asks first: returns {status: 'proposed', approval_url} and runs when the owner approves (on their page, or by your calling again with their approval). The last column says what comes before a call. A tool that takes an idempotency_key needs a new one for each distinct call; the same call sent again with the same key (a retry after a timeout) is answered with its first answer, within a day and while that answer is still true. update_landing_page makes a new preview on every write, revise, edit or preview_html, and on every "build_site" that builds, whatever the key.
